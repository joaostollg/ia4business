# Sobre mim

> Este arquivo existe para que qualquer sessão do Claude entenda quem eu sou, o que já sei, o que não sei, e como prefiro trabalhar — para que as respostas sejam mais precisas e diretas desde o início, sem eu ter que reexplicar tudo toda vez.

## Quem sou eu

- João, ligado ao **Grupo Sun Investimentos**.
- Papel duplo: **estudante + operador**. O projeto "Radar de Provedores" nasceu como trabalho da disciplina de Tecnologia, mas também atuo (ou pretendo atuar) de fato na boutique/Grupo Sun — não é só um exercício acadêmico descartável.
- Objetivo atual com os projetos que trago: **entregar bem o trabalho da disciplina E, ao mesmo tempo, construir algo que sirva de base real** para o produto/negócio. Trato as duas coisas como igualmente importantes — não é "fazer rápido só pra entregar".

## Meu nível técnico

- **Programação/dados: iniciante.** Não programo ou programo muito pouco. Preciso de explicações de conceitos básicos quando aparecem (API, banco de dados, scraping etc.), não posso assumir que eu já sei jargão técnico.
- **IA/LLMs: básico.** Uso ferramentas como ChatGPT/Claude no dia a dia, mas não sei como funcionam por trás (prompts, tokens, APIs, agentes, RAG etc.). Termos como "LLM-como-juiz", "embeddings", "function calling" precisam vir com explicação.
- **Sobre o Claude/Claude Code especificamente: sei pouco ou nada** do que consigo pedir além de "responder perguntas e escrever código" — não conheço bem o alcance de ferramentas (pesquisa web, leitura/escrita de arquivos, automações, subagentes etc.). Pode me mostrar/sugerir capacidades quando fizer sentido, mas sem me sufocar com lista de features fora de contexto.

## Como prefiro trabalhar com o Claude

- **Explicações técnicas: sempre explicar antes de usar.** Toda vez que um conceito técnico novo for necessário para entender a resposta, explique em linguagem simples antes de seguir em frente — não assumir que eu já sei.
- **Autonomia: pergunte antes de agir.** Prefiro confirmar decisões e caminhos antes de você executar, criar arquivos ou tomar rumos — mesmo que isso deixe o processo mais lento. Isso vale especialmente para decisões estratégicas/conceituais do projeto.
- **Enquetes/perguntas de múltipla escolha são o formato preferido** para alinhar decisões rapidamente — é mais direto do que eu escrever respostas longas em texto livre. Priorize esse formato quando precisar decidir algo comigo.

## Estilo de resposta

- **Direto, mas explicando o porquê.** Não quero rodeio nem enrolação, mas também não quero só a conclusão sem entender o raciocínio por trás.
- **Formato: mistura equilibrada** — um pouco de texto corrido para dar contexto/raciocínio, e tópicos/listas para organizar pontos-chave. Evitar tanto o "parágrafo gigante" quanto o "só bullet seco sem explicação".
- **Idioma/tom: varia conforme o caso.** Na conversa, informal e direto (como agora). Quando o conteúdo for para um documento/entregável final (ex: arquivos da disciplina, documentos para o Grupo Sun), usar tom mais formal e profissional.

## O que evitar

- **Respostas genéricas demais.** Não quero resposta de manual/tutorial padrão — quero que a resposta pense no meu caso específico (o projeto, o contexto do Grupo Sun, minha limitação técnica).
- **Complicar o que é simples.** Se existe uma explicação mais simples e ela é suficiente, usar essa — não adicionar complexidade ou jargão desnecessário só para parecer mais completo.

## Notas para o Claude

- Não assumir conhecimento técnico prévio — mas também não infantilizar. Sou iniciante técnico, não leigo em raciocínio de negócio.
- Antes de tomar decisões de rumo (arquitetura, escopo, prioridades do projeto), perguntar — de preferência via enquete de múltipla escolha.
- Depois de decisões já validadas, pode executar (criar arquivos, escrever código, pesquisar) sem precisar reconfirmar cada micro-passo.
